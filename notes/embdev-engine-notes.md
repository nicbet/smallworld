# I Created my own Voxel Game Engine from Scratch

Voxels are volumetric pixels, meaning instead of a 2D image, it represents a 3D volume. This allows for a quantified representation of the entire world into a single global grid, allowing for real-time construction, destruction, perfect voxel physics interactions, and perfectly simulated light. But, there's no standard voxel game engine, so we have to build it ourselves. The rendering is split into two methods, static and dynamic. Static rendering is performed on a large 3D voxel grid. From the camera, we cast a ray for every pixel. If the ray collides with a voxel, it colors that pixel the color of the voxel. Dynamic grids use a similar technique, but the starting point of the ray is reconstructed from a rasterized triangle of the object's bounding box. The devil is in the details, though. Can't store individual colors in each grid cell, as it would use far too much memory. So, instead, you store an 8-bit value as an index to a color map. To speed up the ray traversal, we can use a hierarchical grid. This involves storing a lower resolution version of each grid. You step through the low resolution grid till hitting a non-empty cell, then stepping down in detail. This allows us to skip large empty regions in lower resolution grids. Since the color data is only required in the highest resolution grid, we can use a bit mask representation for the lower resolution grids. This results in an eight times memory reduction, as each voxel is represented by a single bit. This can speed up ray traversal, as it reduces the memory throughput, as well as reducing the memory footprint. That was all just to get pixels on the screen.

Now, we need to make it actually look good. Ray tracing is the holy grail of graphics programming, usually requiring extreme complexity. Since we are already casting rays, the implementation becomes much easier. After the normal and depth pass, you can reconstruct the ray's position in global space.

You can cast scattered rays from the hit location, stepping through the scene. You can also mark certain indexes as emissive. As the ray collides with an emissive voxel, it can collect lighting data, illuminating that pixel. Or, we can have reflective materials. When a ray hits a reflective material, rather than scattering the ray, it is perfectly reflected. For dynamic object shadows, we can use a traditional shadow map where we render all dynamic objects from the sun with an orthographic perspective. Then, sample the shadow map when determining if objects are in shadow. The final step with the lighting is hard shadows. You can directly cast a ray towards the sun. If it collides with a voxel, it is in shadow. The big problem here is noise. For real-time performance, we have to use a half-resolution ray tracing pass, as well as fairly low sample counts. Since we are already using a voxelized look, we can average all rays that hit a voxel. This significantly reduces the noise at only the cost of being more stylized. Additionally, we can blur the hit voxels with its physical neighbors to smooth the per voxel lighting. This ray to voxel mapping also gives us a huge optimization. We can reduce the number of rays cast for the shadow map, since we can change from ray per pixel to ray per voxel hit. The final optimization is temporal accumulation. This is simply averaging the ray trace pass between frames. This produces more stable lighting at the cost of smearing and delayed lighting updates. And that is all the rendering logic. Coding a custom physics engine for voxels sounds like an absolute nightmare. Luckily, this step is actually fairly easy. All we need to do is to adapt the existing engines contact generation logic with voxels. For this, I chose Jolt physics. Jolt is an extremely optimized, multi-threaded physics engine, so we can have many physics objects in the scene at once.

Jolt also has many handy built-in features, like joints and rag dolls. We can alter Jolt to narrow phase contact solver, so when two objects overlap, use a custom contact generator logic. It iterates over every voxel, checking if the radius around on voxel overlaps with the radius of the voxel of the other grid. An optimization we can use is the fact that a face can only contact a corner and an edge can only contact another edge or a corner. This means we can significantly reduce the voxels checked. To adapt this to Jolt Physics, as well as saving time on the solver, we must filter the contact points down the four most extreme points. Solving the extreme points will make most other points redundant anyway. The destruction is fairly simple. The engine cannot handle large destruction of structures, mostly just small objects. When cutting an object, we perform a flood fill to determine if all voxels can be reached and if the object is still attached. And with that, that is everything I have done for this game engine. It is currently suited for small-scale scenes, mostly for interiors, with destruction of only small objects. For larger maps, we need to adapt the destruction to handle large-scale structures similar to Teardown. As well as modifying the rendering logic to allow for chunk streaming to have infinitely sized world. This game engine also has some inherent limitations. Dynamic objects do not exist in the global grid. This means bounced rays cannot collide with dynamic objects. This results in not being able to have emissive dynamic objects, as well as dynamic objects not being able to occlude light. Anyways, that's all I have so far.
